# Spec: responsive task interactions in the existing mobile app

Tracker: [Spec #8](https://github.com/jellotheman/gamified-todo/issues/8) · ready-for-agent.

Discussion synthesized into an implementation specification, 9 October 2026.

## Problem Statement

The dark retro frontend has the right overall identity, but everyday actions still require too much space and attention: an always-open composer dominates the screen, task menus and editors fill the screen, completed titles are struck through, and prominent server-waiting messages make quick task actions feel slow. The previous thin body font is also harder to read than the user wants.

The user wants an efficient phone task loop: capture from a persistent Add control, tap a title to edit, find secondary actions in compact surfaces, complete work and undo nearby, and see useful changes immediately while the app saves. This must remain an honest private task app when a request fails or arrives late, rather than silently losing drafts, duplicating tasks or showing another account's pending content.

## Solution

Keep the existing Expo React Native mobile product and dark retro direction. Use the sturdier Pixelify Sans Medium body font with the existing Pixelify Sans SemiBold headings and readable system fallback. Replace the always-open composer with a persistent bottom-center Add control opening the same compact title-only editor used for editing. Use compact accessible menus/sheets, direct title editing, accessible overflow and optional swipe actions. Completed is collapsed by default and remains readable when opened.

Project owner-scoped local operation overlays over confirmed saved data so add, edit, completion, undo and guarded delete respond immediately. Small local status and recovery controls distinguish saving, failure and confirmation. Smooth motion is required throughout the task loop: tactile press feedback, compact sheet transitions, finger-tracking swipes, completion transitions and orderly list reflow. Keep existing transactions, privacy, deterministic saved ordering and bounded subscriptions; provisional presentation must never manufacture timestamps, saved counts or rewards. Browser testing in Codex exercises this same Expo app as a simulated user; it is not a second web product.

## User Stories

1. As a phone task user, I want a persistent bottom-center Add task control, so that capture is reachable without scrolling to the top.
2. As a phone task user, I want Add task to open a compact title-only editor, so that my list has more useful space when I am not capturing.
3. As a task user, I want create and edit to share familiar controls and validation, so that I do not need to learn two different forms.
4. As a task user, I want a title tap to open editing directly, so that a common action takes one deliberate tap.
5. As a task user, I want a compact task menu with Edit and Delete, so that secondary actions do not occupy a full screen.
6. As a task user, I want visible accessible overflow even when swipe is supported, so that actions are discoverable and usable without gestures.
7. As a touch user, I want an optional partial swipe to reveal Edit and Delete, so that I can act efficiently without opening a menu.
8. As a touch user, I want a full completion swipe to Complete an active task or Undo a completed task, so that its meaning matches the existing task model.
9. As a task user, I want swipe reveal and completion gestures to avoid accidental actions during vertical scrolling, so that browsing the list is safe.
10. As a task user, I want completed titles readable without strike-through, so that I can recognize and edit finished work.
11. As a task user, I want Completed collapsed by default with a clear expand/collapse control, so that current work stays prominent.
12. As a task user, I want completion feedback and Undo beside the action area even when Completed is collapsed, so that I can correct a mistake without hunting for the moved row.
13. As a task user, I want an immediate visible new task after a valid create submission, so that I know capture worked locally while it saves.
14. As a task user, I want edited text to appear immediately, so that I do not wait for the server to see my intended change.
15. As a task user, I want completion and undo to update local section membership immediately, so that checking tasks feels responsive.
16. As a task user, I want a confirmed delete request to remove its row immediately with recoverable local status, so that deletion feels responsive without hiding a failed save.
17. As a task user, I want pending and failed changes visibly distinguished from saved data, so that immediate feedback does not mislead me about persistence.
18. As a task user, I want compact status and retry near the affected row or its recovery placeholder, so that one slow request does not produce a large global warning.
19. As a task user, I want retries to reuse the original submitted identity and payload, so that uncertain saves cannot duplicate a task or silently change what I requested.
20. As a task user, I want Undo during a pending completion to retain my latest intention and serialize writes, so that requests cannot race and leave the wrong final state.
21. As a task user, I want repeated same-action taps or gestures coalesced, so that impatience does not issue duplicate mutations.
22. As a task user, I want server acknowledgements and independently arriving list observations reconciled without duplicate rows or flicker back to old values, so that my intended change remains understandable.
23. As a task user, I want reconciliation to work when a task falls outside a bounded list window, so that an acknowledged operation does not leave an endless saving row.
24. As a task user, I want an invalid title to show its error next to the field and focus that field, so that I can correct it immediately.
25. As a task user, I want keyboard Done and Save to submit one valid operation, so that the editor works naturally with the keyboard.
26. As a task user, I want dismissing an unsaved editor to retain its draft during my current session, so that an accidental dismissal does not force retyping.
27. As a task user, I want a submitted editor to close promptly while its retry payload is retained outside the editor, so that saving does not block the rest of the list.
28. As a task user, I want an explicit guarded delete with the task title and Keep task, so that permanent removal is deliberate.
29. As a task user, I want no misleading delete Undo after dispatch, so that the interface does not promise an operation the current repository cannot safely reverse.
30. As a task user, I want section loading, cache/unconfirmed, failure, retry and paging retained, so that compact presentation does not remove existing recovery.
31. As a task user, I want collapsed Completed to retain history state and pending recovery, so that collapsing a section does not cancel saves or erase loaded windows.
32. As a signed-in user, I want Account and Back to tasks to preserve my current-session drafts and operation recovery, so that normal navigation does not discard work.
33. As a signing-out user, I want private content and overlays hidden immediately with the existing recovery controls, so that sign-out uncertainty does not expose my tasks.
34. As a user switching accounts, I want drafts, operation overlays, timers and listeners purged and late callbacks ignored, so that private activity cannot leak between owners.
35. As a screen-reader user, I want labeled completion, overflow, editor and recovery controls with state announcements, so that I can complete the same task loop without gestures.
36. As a user with large text, I want sturdier readable body text and expandable surfaces, so that task titles, status and editor controls remain legible.
37. As a phone user, I want bottom controls and sheets to respect safe areas and the keyboard, so that neither the keyboard nor system chrome blocks an action.
38. As a user who prefers reduced motion, I want completion and sheet feedback to respect that preference, so that responsiveness does not depend on distracting motion.
39. As a user on an unreliable connection, I want failures to preserve retry identity and explain uncertainty, so that the app does not pretend it has durable offline saving.
40. As a task user, I want provisional changes excluded from saved progress or rewards, so that fast presentation never fabricates an achievement.
41. As a task user, I want smooth sheet entry/exit, checkbox feedback and row reflow, so that actions feel connected and pleasant rather than abrupt.
42. As a touch user, I want swipes to track my finger and return naturally when cancelled, so that gesture outcomes feel predictable.
43. As a task user, I want Completed expansion and nearby Undo feedback to animate coherently, so that I understand what appeared, moved or disappeared.
44. As a user who enables reduced motion, I want equivalent immediate feedback without spatial transitions, so that I can use every feature comfortably.
45. As a task user, I want new captures available while earlier independent tasks save, so that slow requests do not block the next thought.
46. As a task user, I want animations to leave scrolling, input and pending operations responsive, so that visual polish does not delay my work.

## Implementation Decisions

- **Product and data boundary:** this remains one SDK 57 Expo Go React Native mobile app using the current identity, private repository and schema: title-only tasks with server-created timestamps and nullable saved completion timestamp, and the existing profile. Preserve private owner checks, transaction semantics, confirmed-only repository observations and runtime configuration. This spec deliberately changes local interaction/presentation semantics; it does not change backend persistence or add task fields.
- **Visual continuity and type:** retain the existing dark neutral palette, warm accent, outlined tactile controls and pixel heading identity. Use the currently selected local Pixelify Sans Medium for body, field, control and supporting text; retain Pixelify Sans SemiBold headings. Keep OFL notices and readable system fallback during loading/failure and for unsupported characters. Do not restore thin VT323 body text. Check actual small text and large-text rendering; do not achieve compactness through tiny type or fixed-height clipped labels.
- **Reusable native controls:** retain the selective existing reusable control foundation and prefer maintained, free, Expo Go-compatible native menu/sheet and gesture components behind small app-owned adapters. Verify compatibility with the installed Expo/React Native versions, accessibility, keyboard and reduced-motion requirements before adopting them. Reuse existing primitives where adequate. Do not add a complete UI kit, alternate styling framework, hand-written gesture engine or inaccessible overlay merely to imitate a screenshot. Record selected versions, source/license notices and compatibility evidence. A Figma artifact or connected design service is not a prerequisite.
- **Main layout:** remove the always-open capture form. Keep Tasks, Account, Active rows and an expandable Completed section. Fix one labeled Add task action at bottom center within the safe area; reserve list padding so it never covers the last row, recovery controls or paging. It remains on the task surface, not over Account or an open editor. With an editor open, use the editor's reachable Save/Cancel controls and keyboard avoidance instead of placing another Add over the keyboard.
- **Shared editor:** use one compact, accessible create/edit surface containing heading, labeled title field, local validation and Save/Cancel. Create starts with the current create draft; edit starts from that task's latest effective title unless a retained unsaved edit draft exists. Title tapping goes directly here. Menu/sheet content grows or scrolls for long titles, large text and open keyboard instead of becoming an arbitrary fixed-height panel. Focus the field when opened; on invalid submission show the local error and keep/focus the field. Validation preserves the existing trimmed 1–200-character bound. Keyboard Done and Save share one synchronous submit guard.
- **Editor dismissal and retention:** before dispatch, Cancel, platform Back and supported sheet dismissal close the surface without a write and retain that owner's draft for the same create/edit context during this mounted session. Reopening resumes it; successful submission clears that unsent editor draft after freezing the operation payload. Retained edit drafts are invalidated if the task is confirmed deleted. Submitted payloads are immutable recovery state, not editable drafts. A valid submit dispatches once, closes promptly and puts saving/retry on the list; closing afterward cannot cancel the request. An unresolved create is represented by its own provisional row and fixed retry payload. Clear the submitted editor draft and permit another independent capture immediately, allocating a distinct stable ID for each new valid submission. Coalesce repeated button/keyboard events for the same submission before the editor resets; do not mistake an explicit subsequent capture for a retry of an earlier one. Each provisional capture has independent status/retry using its original ID/title, and retries never consume the new editor draft. Other independent task operations remain usable. No draft or overlay durability is promised across remount/restart.
- **Compact actions and deletion:** overflow opens compact Edit task/Delete task actions; title tap is the direct edit route. Delete then opens a compact confirmation showing the full task title, Keep task and Delete task. Dismissing before dispatch is cancellation; after confirmation/dispatch there is no cancellation or delete Undo. Remove the effective row immediately, retain a compact recovery entry at its former section position, and show Saving deletion or failed/unconfirmed deletion with Retry. Successful confirmation removes that entry. Retry reuses the same ID; no restore/create is fabricated. Do not allow edit/completion on a task while its deletion is unresolved.
- **Gestures:** partial swipe reveals Edit/Delete without dispatching; full completion swipe in the opposite direction dispatches Complete for Active or Undo for Completed, never Archive. Full swipe toward the revealed actions must not bypass guarded deletion. Reveal and completion gestures track the finger smoothly; cancellation springs back without dispatch. Set deliberate displacement thresholds, resist accidental activation while vertically scrolling and allow only one revealed row at a time. Close revealed actions when a menu/editor opens or the row leaves the effective list. Disable conflicting gestures while their operation is unresolved. Screen readers/reduced-motion users retain labeled tap controls; gestures are optional accelerators, never the only route. For interfaces where swipe is unavailable, overflow and completion still expose the complete loop.
- **Required motion contract:** smooth, coherent motion is an implementation requirement, not optional decoration. Animate compact editor/menu sheet entry and exit; tactile pressed-state feedback; finger-tracking swipe reveal/full-action and spring return on cancellation; completion check feedback and row movement/reflow; Completed expand/collapse; and transient Undo entry/dismissal. Use a shared short-transition baseline of 150–250 milliseconds (approximately 200 milliseconds for row/reflow and expansion), with maintained gesture-library spring defaults tuned for predictable settling. These are design tokens, not brittle exact-duration acceptance tests. Preserve the optimistic state change immediately when an action is accepted; neither a server response nor finishing an animation gates dispatch, future input or visible state. Use the existing motion/gesture foundation and maintained Expo Go-compatible primitives with native UI-thread execution where appropriate; do not write a custom engine or introduce another framework. Animate bounded visible work rather than rebuilding every task on each gesture frame. Prevent scroll jumps, layout clipping, forced focus movement and tap/swipe/vertical-scroll conflicts; account for safe areas and keyboard resizing. Retain focus according to the explicit editor/menu rules, rather than shifting it merely because a row animates. Respect the OS reduced-motion preference: replace spatial movement and springs with instant updates or a subtle opacity cue while preserving all controls and statuses. No expensive particles, confetti, streak spectacle, artificial waiting or continuous ambient animation.
- **Completed and nearby Undo:** Completed starts collapsed for each new task-screen session, with an accessible expanded state; opening Account and returning preserves the user's current expansion choice and loaded windows. Collapsing hides saved rows but does not unsubscribe, cancel operations or hide failed recovery. Show a small task-specific completion message and Undo near the task list's action area immediately after Complete. Keep Undo available through the pending/unconfirmed phase and for five seconds after the latest desired completion is confirmed; pause expiration while that action has focus or is being announced, and do not depend on this timed control as the only undo route. Completed rows provide persistent ordinary Undo when expanded. Multiple unresolved completions retain individually labeled compact recovery, even if only the latest confirmed transient message is displayed. Completing does not automatically expand Completed. Use checked state, section membership and secondary styling instead of strike-through.
- **Operation identity and immediate projection:** represent create, rename, desired completion and delete as owner/session-scoped local operations with stable task ID, frozen retry payload, latest local revision, last-confirmed record if one exists, and pending/failed/acknowledged-awaiting-reconciliation phase. Project them over confirmed bounded windows instead of mutating confirmed records or making fake Task timestamps. Add displays a provisional Active row before saved ordered rows; rename substitutes the title; completion immediately records the destination intent and presents one effective task occurrence, using a short visual check/row transition before settling in the destination when motion is enabled; undo reverses that effective membership; delete suppresses the row and displays its compact recovery entry. Provisional ordering is explicitly local operation order, not server timestamp order. One effective task ID may appear only once across both sections. Collapsed destinations still show nearby operation feedback. Never change confirmed saved counts/rewards from this projection.
- **Pending serialization and Undo:** allow at most one dispatched mutation per task at a time. Coalesce repeated identical submissions; do not issue parallel rename/completion/delete for the same task. Completion Undo may record one latest opposite desired boolean while an earlier completion write is in flight; update the local projection immediately, then dispatch the latest queued desired state once the prior request settles. Repeated intention changes replace that queued boolean rather than growing a queue. Earlier callbacks cannot clear or reverse a newer revision. On a rejected earlier request, dispatch the latest queued desired state only as a transaction to establish that explicit final state; a rejected response does not prove that an uncertain prior write never committed. Retry failures using the latest frozen intended state. Disable conflicting edit/delete until completion reconciliation is resolved; separate tasks remain independent.
- **Truthful reconciliation:** a resolved mutation establishes server acknowledgement, but cannot supply invented created/completed timestamps or justify applying a stale list window. Retain an acknowledged local projection until matching confirmed data establishes its latest result. Accept a matching confirmed observation arriving before or after acknowledgement, without duplicate insertion or an old promise erasing a newer intent. For rename/completion, reconcile by ID and the requested title/desired state; for creation use its original ID; for deletion require confirmed absence, not merely omission from a bounded query. Preserve deterministic saved ordering and newest-confirmed cross-section membership once local projection retires.
- **Bounded windows and absence:** keep separate initial 25-row windows, lookahead and 25-row expansion with complete live-window replacement. A task missing from one or both bounded windows is not proof of deletion or a failed save. If an acknowledged result cannot be reconciled by the current windows, obtain bounded owner-scoped server confirmation for that affected ID (record or confirmed absence), rather than expanding every list or retaining an endless overlay. Any confirmation helper stays behind the private repository boundary and is exercised through existing screen/repository seams; it introduces no new public product surface. Require server-confirmed record timestamps and ignore cache/pending metadata for this purpose. A confirmation-read failure leaves an explicit compact unconfirmed state with retry. Once confirmed outside the loaded windows, retire the overlay and honor the saved window boundary; do not indefinitely pin a saved task outside the query or invent a position. Refresh/reobserve an affected bounded window when needed so a stale pre-operation source window cannot resurrect a just-reconciled row. Later genuinely fresh confirmed updates remain authoritative.
- **Failure and recovery:** preserve latest optimistic presentation with an explicit local failed/unconfirmed marker and frozen Retry payload rather than silently claiming success or losing input. A deleted row uses its recovery entry; a collapsed completed destination retains a visible recovery entry outside the hidden rows. When confirmed data already proves the intended result despite a rejected promise, resolve the operation rather than show a false retry. Do not infer connectivity from cache metadata alone. Retry repeats the operation identity/state; it does not allocate a new draft ID. If server confirmation proves a task was deleted elsewhere, stop impossible rename/completion retries, discard its local row and explain that outcome. No durable offline queue, background sync promise or automatic unlimited retry.
- **Section status and privacy:** compact loading/unconfirmed/cache/error status remains section-specific; confirmed empty is not shown before confirmed data. Preserve explicit section retry and paging. Account navigation keeps the mounted task session, drafts and operation state while hiding inaccessible task content. Sign-out hides and purges private content immediately using the current recovery gate; owner/session changes and unmount cancel listeners, local timers/queued dispatches and overlays, and ignore old promises or confirmation reads. Returning after failed sign-out reloads confirmed data rather than reviving a purged private operation. Restored identity alone does not bypass account-readiness checks.
- **Accessibility and responsiveness:** maintain at least 48-unit actionable targets, non-overlapping hit areas, text scaling, safe areas, scrolling and keyboard reachability. Overflow, completion and Undo have task-specific accessible names and checked/busy/disabled state. Menu/editor focus enters the relevant field or heading; dismiss restores focus to a surviving originating row/control or Add if that row was removed. Announce concise pending/failure/completion states politely; use assertive announcements for actionable field errors without repeated long server warnings. Hidden completed rows and behind-sheet content are not reachable to accessibility navigation. Apply the required shared motion contract and its reduced-motion alternative while providing immediate state feedback without a server latency guarantee or an artificial completion delay.
- **Delivery workflow:** work and commit on dev, using the existing active development server without restart and one implementation/repair agent at a time. Run root checks and review before source promotion. GitHub Actions currently checks source; pushing/merging does not deploy the app or Firebase. Push only under explicit user authorization, verify the exact dev feature SHA before any authorized normal dev-to-main merge and sync main back into dev. No worktree, native build, paid service or backend deployment is introduced by this spec.

## Testing Decisions

- Keep the previously agreed highest screen-level seam: render the existing task and identity/account flows with controlled authentication/repository responses. Retain repository contract tests. No new public testing seam is required; operation-state organization is an implementation choice.
- Good tests exercise user-visible action/results and controlled ordering, not internal overlay structures, component nesting, font constants or a library's animation implementation. Prefer focused behavior tests over broad snapshots.
- Add/create/edit tests cover compact editor opening, direct title tap, retained unsent drafts after dismissal, focused local validation, keyboard/button coalescing, immediate provisional add/edit, frozen retry payload, independent subsequent captures with distinct stable IDs and independent operations on other tasks.
- Completion tests cover immediate intended membership with a short visual transition where enabled, collapsed Completed feedback, readable completed titles, accessible expansion, nearby Undo before acknowledgement, serialized opposite intent, repeated gesture/tap coalescing, failure/retry and no stale result reverting latest intent. Use controlled time for transient Undo expiration; verify persistent completed-row undo remains reachable. Exercise a subsequent capture while a previous create is pending and verify each independent retry preserves its own ID/title.
- Delete tests cover Keep task before dispatch, mandatory confirmation, immediate removal/recovery entry, no post-dispatch delete Undo, stable-ID retry, concurrent conflicting controls disabled and reconciliation of confirmed deletion.
- Reconciliation tests deliberately deliver acknowledgement and confirmed observations in either order, rejected promises after matching observations, cross-section windows arriving out of order, task omission due to window bounds, confirmation-read errors, cache/pending data, external rename/deletion and late callbacks. Assert no duplicates, no fabricated saved timestamps/counts, no premature retirement or stale resurrection.
- Motion tests assert immediate action/state availability during transitions, cancelled gestures restoring the resting state without dispatch, one accepted gesture producing one intent, preserved focus/scroll position and equivalent reduced-motion behavior. Do not assert exact milliseconds, spring internals or every intermediate frame. Verify native smoothness, finger tracking and sheet/keyboard behavior on devices; browser automation alone cannot establish these properties.
- Session tests cover Account/back preserving drafts/expansion/operations, sign-out privacy even on failure, owner switch while a completion reversal is queued, unmount and late operation/confirmation responses. No old callback may mutate the next owner's visible state.
- Menu/gesture accessibility tests cover ordinary completion/overflow as alternatives to swipe, revealed action routing, guarded delete and focus restoration. Native gesture threshold/vertical-scroll conflict, keyboard/sheet behavior, VoiceOver/TalkBack and large text require device interaction evidence in addition to controlled tests.
- Run root npm run check. Any dependency/configuration changes additionally require SDK-aware Expo dependency validation and Expo Doctor; read installed-major official docs when adapting native APIs. Keep services free and backend emulator/native build scope unchanged.
- The main Codex coordinator runs browser visual and simulated end-to-end user flows against the same active Expo app at http://localhost:8081, without stopping/restarting the server. Exercise capture/edit/complete/Undo/delete/Account, compact menus/editor, recovery and representative narrow/large-text states where supported. Use isolated disposable development data and clean it up. Browser testing is an additional automation surface, not separate web UX/product work and not proof of native swipe, screen-reader or keyboard behavior.
- Record actual native Expo Go iPhone/Android evidence when available and leave unavailable checks explicitly pending. Review the final complete change on Standards and Spec axes, delegate repairs sequentially and rerun appropriate checks after repairs. Spec preparation itself does not implement these behavior changes.

## Out of Scope

- Dates, reminders, archive, search, lists/projects, priority, notes, subtasks, recurrence, bulk operations, manual ordering or new task/profile fields.
- RPG characters, classes, XP, inventory, currency, achievements, rewards, punitive streaks and #4 daily-goal/count/time-zone work. Provisional actions cannot contribute to future saved progress.
- Delete undo after dispatch, transactional undelete, durable offline queues, persisted optimistic drafts, background synchronization and promises that requests complete within 100 milliseconds.
- A second web application, independent web interaction redesign or browser platform support expansion. The existing Expo browser render is used for Codex testing of the mobile product.
- Replacing the visual framework, building a large custom component/gesture library, paid resources, mandatory Figma authoring or importing screenshot/Habitica artwork.
- Firebase schema/rules/index/environment deployment, backend emulators, cloud/native releases, Functions and automatic application deployment from CI. Git pushes require explicit authorization.

## Further Notes

This spec records the reviewed interaction direction after the earlier dark-retro visual adaptation. It supersedes that adaptation's always-open composer, full-height task surfaces, struck-through completed text and saved-only visible movement for the interactions described here. The underlying server-confirmation and private-account contracts remain authoritative. The body-font readability repair is committed separately as a4581b6, using Pixelify Sans Medium for body/input text and Pixelify Sans SemiBold headings; this spec preserves that direction rather than expanding typography work. An [editable Figma visual reference](https://www.figma.com/design/XLg2tasCMGF2bpUWauBYBo) exists; it is informational visual/flow guidance, while the operation and recovery semantics in this text specification are authoritative. Separate development-tooling work does not belong to this interaction implementation scope.

Keep the later implementation plan compact. Separate a testable interaction slice from a testable operation/reconciliation slice only if that helps implementation; do not create one ticket per gesture, dialog or state. This formal specification is ready-for-agent. No implementation tickets are created here.
