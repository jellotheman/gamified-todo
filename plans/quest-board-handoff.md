## Product and design plan

### Outcome and scope

Deliver a polished personal Quest Board with one-off quests, daily routines, cumulative area progress, and “Pick for me.” Keep the working authentication and account flows. The first complete loop is create a daily quest, complete it, see confirmed progress, and find it available tomorrow.

The agreed defaults are Figma typography, three renameable starter areas, preserved past progress, and polished tap controls. Coins, shops, combat, classes, arbitrary recurrence, calendars, timers, and swipe shortcuts remain outside this delivery.

### Reuse and visual consistency

- Follow the existing charcoal/amber design system, spacing, hierarchy, and control states. Use Pixelify headings and Inter body text, superseding the older all-Pixelify preference. Bundle required fonts and retain source/license notices and readable loading/failure fallbacks.
- Reuse React Native Paper controls, existing icons, font loading, authentication, shared buttons, and inputs. Add small app-owned compositions for quest rows, editor sheets, feedback, and progress. Use an accessible native modal shell and existing animation support; add no complete UI kit or alternate styling framework.
- Provide **Quests** and **Progress**, with **Account** available from a common header. Switching views preserves session drafts and pending operations while hidden surfaces remain inaccessible.
- Use actual device keyboard/status-bar behavior. Handle safe areas, keyboard avoidance, text scaling, focus entry/restoration, and at least 48-unit touch targets. Long content must wrap or scroll. Respect reduced motion.

### Quest interactions

- Show daily routines and outstanding one-off quests. Completed starts collapsed; titles stay readable without strike-through. It contains today's completed routines and paged completed one-offs.
- A persistent **Add quest** opens the shared bottom-sheet editor: title, Once/Daily, and optional area. Default to Once and no area. Preserve the current trimmed 1–200-character title validation. Recurrence is selected at creation; later editing changes title and area.
- Title taps edit directly. Overflow opens compact Edit/Delete actions. Delete requires confirmation explaining that past progress remains. After dispatch there is no promised delete Undo. Dismissed editors retain their unsent draft during the session; valid submissions close promptly and retain their retry payload outside the editor.
- “Pick for me” highlights an eligible one-off from the currently displayed list. It never starts or completes an action automatically and is unavailable without candidates. Normal manual choice always remains possible.
- Give immediate row-level Saving/Retry and completion/Undo feedback. Use restrained sheet, row, disclosure, and milestone transitions. Keep scrolling/input responsive; gestures are not required.

### Growth and area settings

- Start with **Learning**, **Health**, and **Home**, using stable area identities. Account lets users rename these three areas; it does not add a category-management system. A quest may remain uncategorized.
- Completing categorized actions credits at most **one day per area per calendar date**, regardless of the number of actions. Three active days, a missed day, then two active days means five credited days.
- Progress displays credited days and milestones at **5, 15, 30, 50, and 80**. Counts continue after the final milestone. Explain that these represent recorded activity rather than mastery. Missed days never remove progress.
- Celebrate a newly reached milestone only after a confirmed completion. Startup, retries, rerenders, and renaming alone must not replay celebrations.

## Persistence and interfaces

- Keep existing one-off task documents and identities. Missing area data means uncategorized. Preserve old completed tasks without inventing historical credit. Add daily routines alongside current task storage.
- Extend the private repository with routine CRUD, private area-label settings, daily completion observations, completion/Undo, and confirmed progress reads. Normalize quest records behind that boundary so presentation components do not call Firestore directly.
- Use stable completion identities: one current completion record per one-off quest, and one per routine/calendar date. Freeze the device-local date and area when submitting. Retain those values on retries and across late acknowledgements.
- Maintain an area/date contribution count atomically with completion changes. Count dates with positive contributions across full history, independently of loaded task pages. Repeated taps, retries, and concurrent devices must not duplicate contributions.
- Undo removes a completion's contribution. An area loses its day only when the last qualifying contribution is removed. Daily Undo applies to today; one-off Undo remains available from completed history.
- Deletion preserves earned records. Changing a quest's area affects future completions; it does not move old credit. Renaming an area changes its label while retaining its stable identity and history.
- Use the device-local calendar date at submission. Refresh daily availability at midnight and foreground resume, and check the date before actions. Previously recorded dates remain fixed after timezone changes. Handle pending saves that cross midnight using the frozen submission identity/date.
- Project local pending/failed state onto rows without manufacturing saved timestamps or progress. Serialize conflicting operations, preserve stable retry payloads, and ignore late callbacks from old owners/sessions. Account switching and sign-out purge private state and subscriptions.
- Preserve bounded list loading. Observe today's completion state for displayed routines independently of completed-history pagination. Refresh server progress counts after relevant saves, when opening Progress, on resume, and through explicit refresh. Aggregation is a server read, not a realtime/offline listener; unavailable progress is not zero.
- Extend owner-only Firestore rules/indexes with strict schemas and transactional consistency. Keep runtime environment guards and the free setup. The existing default database in `gamified-todo-dev-jellotheman` was verified as Standard/free-tier on 31 October; verify the target before writes instead of provisioning a replacement. Refine exact schemas within these fixed behavior invariants using applicable Firebase guidance.
