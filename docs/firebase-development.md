# Firebase development

The mobile app uses Firebase's modular JavaScript SDK for Auth and Firestore. Native Auth persists sessions through AsyncStorage; web uses browser persistence. Local development uses the existing real development Firebase project on the free Spark plan. Setup is in [mobile development](mobile-development.md).

`apps/mobile/.env.example` contains public development web-app identifiers. Copy it to ignored `.env.local` on first setup. `EXPO_PUBLIC_APP_ENV=development` requires project `gamified-todo-dev-jellotheman`; production requires `gamified-todo-prod-jellotheman`. The selector is mandatory: missing, blank or unsupported values fail both Expo app-identity configuration and Firebase startup. apps/mobile/.env.production.example contains the complete approved public production set as a reference; it is not automatically loaded. For a separately intended production runtime, supply that entire set explicitly. Keep the ongoing local .env.local development configuration unchanged when promoting source to main. Startup validates the project ID **and** approved API key, auth domain and app ID independently of `__DEV__`: Auth chooses its account store by API key, so a project-ID check alone is insufficient. The approved public identifiers live in `firebase-config.ts`; update that allowlist, environment files and regression tests together after an intentional web-app/key rotation. Never store login passwords, service-account credentials or tokens in public app variables.

The authentication screen uses normal email/password operations. The opt-in smoke check validates initialization and temporary local storage; it does not sign in or access the database. Root `npm run check` uses mocks and does not verify live rules or indexes.

## Quest Board schema and verification status

The current local rules and repository are an **uncompiled, undeployed prototype**. An earlier Quest Board rules version compiled in a development dry run; the subsequent area-total and date-validation changes have not been compiled. The development project still has its previously deployed task rules, so the new Quest Board writes are not yet verified against that backend. The existing default development database was inspected as Standard and free-tier; do not create a replacement or attach billing.

The intended owner-private model is:

- `users/{uid}/tasks/{taskId}` retains existing one-off identities and fields: trimmed 1–200-character `title`, immutable request-time `createdAt`, nullable `completedAt`, and optional `areaId` (missing means uncategorized). Old completed tasks are not given invented area credit.
- `users/{uid}/routines/{routineId}` holds a daily quest's title, nullable stable area identity and immutable creation timestamp. The identities are `learning`, `health`, and `home`; `users/{uid}/profile/areas` stores their renameable labels. The historical `profile/settings` daily-goal document remains supported.
- `users/{uid}/routineIdentities/{routineId}` is an immutable identity marker. New routines create it atomically; deletion retains it. Deleting an older existing routine without a marker creates one in the same transaction. This prevents later reuse of those identities.
- `users/{uid}/completions/{completionId}` records quest ID, kind, frozen device-local calendar date, nullable area and creation time. One-off IDs use `once_{taskId}`; routine IDs use `daily_{routineId}_{date}`. Editing an area affects future completions, while deletion preserves earned records.
- `users/{uid}/areaDays/{area}_{date}` retains a contribution count and the completion marker for its most recent change, including zero-count records. `users/{uid}/areaTotals/{area}` retains a total and the date/completion marker of its latest zero-crossing. Completion, day and total changes are intended to be linked atomically; the transaction result can identify a newly reached milestone. Progress display independently reads server aggregation counts for positive area-day records and treats unavailable reads as unavailable.

The repository captures one UID, ignores late responses after session changes, requires acknowledged transactions, retains frozen retry payloads and observes today's completion independently for displayed routines. Task and routine windows are bounded; completed one-off history is paged. `firestore.indexes.json` includes the existing active-task index and a new area-day aggregation index. No durable offline outbox is provided. The area-total design assumes no existing area-day records lacking corresponding totals; verify this before deployment or migration. Previously deleted routines that predate identity markers have no routine document to mark on deletion; if any exist, their orphaned completion identities need a separately verified migration before their IDs can be protected. The identity rules are uncompiled and unverified.

The latest rules require independent review and compiler/live-client validation before use. Test owner and stranger/guest access, exact schemas and real calendar dates, completion/Undo and counter/total linkage, repeated and concurrent operations, deletion history, same-ID reuse and area reassignment. Verify the explicit development target and clean up isolated test data afterward. Mocks do not establish deployed enforcement. The automatic approval reviewer rejected the latest compiler dry run; see the [execution checkpoint](../plans/quest-board-handoff.md#execution-status). No revised Quest Board rules or indexes have been deployed.

The CLI aliases in `.firebaserc` are `dev` and `prod`, with development as the default. Rules changes have no cloud effect until explicitly deployed.

For an authorized manual rules/indexes deployment, authenticate and select the intended alias explicitly from the repository root:

```powershell
npx firebase login
npx firebase deploy --only firestore:rules,firestore:indexes --project dev
```

Use `--project prod` only for an explicitly intended production deployment. GitHub Actions performs checks only. This app has no Functions, backend emulator workflow, automated deployment or billing requirement. Production resources are outside this identity milestone.

## Development identity setup

In the **development** Firebase Console, enable Authentication → Sign-in method → Email/Password (leave email-link login disabled). Keep Spark with no billing attachment. Manually create an ordinary user with a private email, set its Firebase Auth display nickname to `admin`, and send a password-reset email so the user chooses a strong password privately. The nickname grants no privileges. Never assign privileged claims, seed at startup, add a shortcut login, put credentials in `.env`/source/issues, or provision this user in production. Use its normal email/password on the sign-in screen.

Use the complete reset link with `mode=resetPassword`, `oobCode` and a **nonempty** `apiKey`; removing parameters can produce “The selected page mode is invalid.” If the received link has an empty key, request a fresh reset email after Auth provisioning. Do not share the full code or password in an issue. Reset links are single use and expire.

## Historical live development rules verification

After an authorized development-only deployment, use two isolated ordinary email/password test accounts and marked temporary IDs. Verify owner task create/read/query/edit/complete/repeat-complete/undo/recomplete/delete and profile create/read/update. Verify unauthenticated and second-account get/query/create/update/delete are denied. Verify missing/extra fields, title whitespace/length/types, noninteger/out-of-range goals, creation-time edits, non-request-time completions and completed-to-different-timestamp rewrites are denied. Clean up owner data and temporary test accounts. Record outcomes and deployment separately; mocks are no evidence of cloud enforcement.

For the earlier identity rules only, prototype review covered each required attack: public listing and other-account CRUD are blocked by path ownership; create/update ownership injection, schema pollution and privileged-role injection fail exact-field validators; omission, type juggling and excessive titles fail the validators on both write types; immutable creation-time edits and forged completion times fail transition checks; goal overflow/negative/fractional values fail integer bounds. Path traversal/references, counters/replay and mixed public/private content are absent from the schema. Owner-scoped queries match read rules; unknown paths deny access. Task subcollections intentionally work without a parent user document because UID ownership is independent of profile creation. Both update rules invoke their full domain validator. These static review outcomes require the live checks above.

I've set up prototype Security Rules to keep the data in Firestore safe. They are designed to be secure for private owner paths with exact schemas, bounded values, immutable creation timestamps and request-time completion transitions. However, you should review and verify them before broadly sharing your app. If you'd like, I can help you harden these rules.
