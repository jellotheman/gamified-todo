# Gamification research and first feature slice

Researched 9 October 2026. This is research and a proposed feature plan only; the existing scaffold and Hello World screen remain unchanged. Input: the user-supplied transcript of [the video](https://www.youtube.com/watch?v=LXX_qOA5D8E). YouTube could not be fetched, so transcript wording was not independently checked against the recording. Recommendations below are design judgments, not demonstrated effects in this app.

## What survives checking

**Useful direction: meaningful completion, achievable goals and user choice.** The transcript argues against points/badges/leaderboards becoming the product. That is a useful hypothesis, but its blanket claim that these mechanics are documented failures is too strong. The [2024 education meta-analysis](https://link.springer.com/article/10.1007/s11423-023-10337-7) covered 35 interventions and found positive autonomy/relatedness effects and a smaller, statistically significant competence effect (g = 0.277). It also describes discouragement among low-ranked learners. Educational findings do not directly establish productivity-app retention; task counts likewise do not prove mastery. Prefer feedback about actual finished tasks, with no claim that completing more tasks measures skill.

**Feature overload is plausible; there is no universal feature-count threshold.** The [2025 Frontiers study](https://www.frontiersin.org/journals/psychology/articles/10.3389/fpsyg.2025.1671543/full) surveyed 632 Chinese university students about fitness apps and modeled perceived feature richness against exercise-adherence intention. It was cross-sectional and self-reported, not an experiment adding features or measuring retained users. Separately, the [Habitica study](https://www.sciencedirect.com/science/article/pii/S1071581918305135) included a two-week quantitative study of 45 users, all experiencing some counterproductive effect. That does not mean every Habitica user loses productivity. One relevant problem: users could be penalized for failing to record work during busy, productive periods. Keep the task action simpler than the game layer.

**Streak agency matters; neither universal harm nor a day-31 cutoff is established.** The [2023 Belgian study](https://experts.azregents.edu/en/publications/snapchat-streakshow-are-these-forms-of-gamified-interactions-asso/) surveyed 2,483 early adolescents and examined associations between Snapchat streaks, problematic use and FOMO. Association is not causation, and adolescent messaging differs from adult task planning. [Duolingo reports](https://blog.duolingo.com/how-duolingo-streak-builds-habit/) improved daily activity after offering more streak flexibility, but this is company-reported evidence. For our first slice, an editable daily goal avoids a streak reset entirely. Missed goals cause no lost progress, health damage or payment to recover.

**Completion rings are a reasonable UI experiment, not a proven causal engine.** I could not corroborate the transcript's exact 49.5%/160,000 figure from a primary source in this brief search. [RAND's Apple Watch/Vitality research](https://www.rand.org/pubs/research_reports/RR2870.html) reports a 34% association with more tracked activity days in a program containing financial incentives and watch repayments. It does not isolate ring visuals; indeed, it studies loss-framed incentives. Neither a sleep association nor perceptual closure alone proves rings cause behavior change. Use a progress bar or ring with a readable count because it makes progress understandable; test its usefulness here. Variable reward packs, brand growth statistics and regulatory assertions were not verified or used to justify features.

## Stack and first slice

Keep the repository's Expo SDK 57, React Native, TypeScript, Expo Router, Firebase JS SDK and AsyncStorage. [Expo's Firebase guide](https://docs.expo.dev/guides/using-firebase/) supports JS Auth/Firestore in Expo Go; native React Native Firebase requires custom native builds. Use Auth identity plus direct Firestore SDK calls as the API and hosted database; no Express server, SQL ORM or separate backend is needed. Keep a narrow task repository interface and ordinary React state.

Remain on Spark. [Firebase pricing](https://firebase.google.com/pricing) supplies Firestore Standard free quotas (1 GiB, 50,000 reads/day and 20,000 writes/day) and non-phone authentication. Bound task listeners to avoid unnecessary reads. [Functions deployment requires Blaze](https://firebase.google.com/docs/functions/get-started), despite a no-cost usage allowance: it conflicts with the no-billing requirement and remains outside scope. No MCP installation is required for this plan. No real Firebase configuration or deployment occurred during research.

Recommendation: build one usable task loop in three grouped milestones: durable email/password identity and private Firestore storage; task add/list/edit/delete with reversible completion; and forgiving daily focus progress with an adjustable goal. Derive progress from actual completed tasks, allow undo, and never deduct health or retained progress for a missed day. Leave recurrence, reminders, collaboration, currencies and leaderboards for later. A native progress bar and readable count avoid another dependency in this slice.

Evaluate task completion usefulness and whether progress feels supportive after real phone use. Session length or repeated reward taps alone are poor success criteria.
